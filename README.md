# Blobs

A 3D couch co-op space exploration game (1–4 local players), built in Unity 6 (6000.6.5f1) with URP.
Players explore a shared 3D world on one screen. Research happens in a 2D minigame that each player
plays in their own screen panel while the others carry on exploring.

## Getting started

1. In Unity Hub, choose **Add → Add project from disk** and select this folder. Open it with **6000.6.5f1**.
2. Open `Assets/_Project/Scenes/Game.unity` and press **Play**.
3. **Join**: press any button on a gamepad, or a key on either half of the keyboard. One keyboard can seat
   two players, one on the WASD side and one on the arrow-key side, so you can test co-op without gamepads.
4. Walk to one of the four terminals and press **Interact** to start researching.

| Action | Gamepad | Keyboard (left) | Keyboard (right) |
|---|---|---|---|
| Move | Left stick | WASD | Arrow keys |
| Jump | South (A / Cross) | Space | Right Shift |
| Interact | West (X / Square) | E | Enter |
| Research: move probe | Left stick / D-pad | WASD | Arrow keys |
| Research: lock signal | South (A / Cross) | Space | Right Shift |
| Research: leave | East (B / Circle) | Esc | Backspace |

In the placeholder minigame, steer your probe onto a grey node and press lock. Lock every node to finish.

The scenes, prefabs and materials are generated by **Tools → Blobs → Build Scaffold**
(`Scripts/Editor/ScaffoldBuilder.cs`). Re-running it **overwrites** them, so stop using it for an
asset once you start editing that asset by hand.

## How the pieces fit together

- **Joining**: `LocalJoinController` on *Coop Session* listens for any button press. An unpaired gamepad
  joins as a new player. A key on the keyboard joins the scheme (`KeyboardLeft` or `KeyboardRight`) that key
  is bound to, if that half is free. The two keyboard schemes must never share a key. Then `CoopSession` assigns the player a slot (0–3), a colour and a spawn point,
  and adds them to the camera's target group. If a controller disconnects, that player keeps their slot
  and their character greys out until the controller reconnects.
- **Camera (dynamic split-screen)**: `SplitScreenDirector` gives every player slot a view camera with the same
  angle and lens.
  - While the group fits on screen, every view frames the whole group, so they are identical and only one renders.
  - Past the maximum zoom-out (`_maxDistance`), the screen splits instead. Players are clustered, with hysteresis,
    so players near each other share a view. Each cluster's view slides just far enough to keep that cluster on
    screen (`SplitScreenMath.SplitFocus`).
  - The views render to textures. A composite camera draws them through `SplitScreenComposite.shader` as a
    Voronoi split, with one cell per view centred on its players. Dividers appear only between cells that
    actually differ, and fade in and out as views separate and merge.
  - Research panels draw on top of all of this.
  - Cost: each split view renders only the bounding box of its own section (`Camera.rect` plus a cropped
    projection, `SplitScreenMath.CroppedProjection`). Total pixels stay at about one screen however many ways it
    splits (`RenderedScreenFraction`, which the tests check). Per-view work is still repeated: culling, draw calls
    and especially shadow maps. That is the next thing to profile on console hardware.
- **Research (one panel per player)**: `ResearchTerminal` → `ResearchSessionManager.TryBegin`:
  1. switches *that player's* input to the `Research` action map (the others keep `Player`),
  2. loads `Research.unity` additively with `LocalPhysicsMode.Physics2D`, which gives the copy its own 2D physics world,
  3. moves the copy 10,000 units away (×slot) so its orthographic camera sees only that copy,
  4. places the camera's viewport using `ResearchPanelLayout`: corner panels while anyone is exploring;
     full screen, halves or quadrants once everyone is researching.
- **Writing a minigame**: subclass `ResearchMinigame`. Read input and physics only through `Context`,
  because several copies run at once. Don't use singletons, statics, `Time.timeScale`, or global
  `Physics2D` queries. Pause a copy with `IsPaused`. Call `Finish(...)` when it's done. The base class
  handles the Exit button and steps the local physics scene.

## Source control

- Git with LFS: binary art and audio are tracked by LFS through `.gitattributes`. Run `git lfs install` once per machine.
- Asset serialisation is **Force Text**, so scenes and prefabs are diffable YAML.
- For merging scenes and prefabs, register Unity's Smart Merge tool once:

  ```
  git config merge.unityyamlmerge.name "Unity SmartMerge"
  git config merge.unityyamlmerge.driver "'C:/Program Files/Unity/Hub/Editor/6000.6.5f1/Editor/Data/Tools/UnityYAMLMerge.exe' merge -p %O %B %A %A"
  ```

## Tests

- **EditMode** (`Tests/EditMode`): pure logic such as the panel layout.
- **PlayMode** (`Tests/PlayMode`): smoke tests that load `Game` and simulate gamepads with the Input System
  test framework. They cover:
  - the camera before anyone joins
  - gamepad and shared-keyboard joining
  - one player opening and closing a research panel
  - the split-screen splitting into two, three and four views and merging back.

  Set `BLOBS_CAPTURE_DIR` to a folder to save the composited split-screen frames as PNGs. This needs a
  graphics device, so leave out `-nographics`.

Run them from the **Test Runner** window, or from the command line with Unity closed:

```
Unity.exe -batchmode -projectPath . -runTests -testPlatform PlayMode -testResults results.xml
```
